  <name>Task 1: Add semantic Contact-field comparison for changeset detection</name>
  <files>src/sync/vcard_write.rs, src/sync/push.rs, src/commands/sync.rs</files>
  <behavior>
    - Test: contact_fields_changed returns false when Contact CRM fields match cached snapshot
    - Test: contact_fields_changed returns true when name differs from cached snapshot
    - Test: contact_fields_changed returns true when email list differs from cached snapshot
    - Test: contact_fields_changed returns true when phone, company, role, website, or birthday differ
    - Test: contact_fields_changed returns true (changed) when no cached snapshot exists (first push)
    - Test: compute_push_changeset with matching snapshot produces zero updates (regression for the 985 false positive bug)
    - Test: compute_push_changeset with changed name produces one update
  </behavior>
  <action>
    The root cause (from .planning/debug/push-changeset-false-updates.md): compute_push_changeset uses `serialized == *cached_text` string comparison between merge output and raw cached server vCard. This always differs due to property reordering, parameter loss, and encoding differences.

    Fix approach: Compare Contact CRM fields semantically instead of comparing serialized vCard strings.

    1. In src/sync/vcard_write.rs, add Contact snapshot caching:
       - Add `contact_snapshot_dir(crm_root: &Path) -> PathBuf` returning `crm_root.join(".sync").join("contact-snapshots")`
       - Add `cache_contact_snapshot(crm_root: &Path, source_id: &str, contact: &Contact) -> Result<()>` that serializes the CRM-mapped fields (name, email, phone, company, role, website, birthday) as a simple JSON file to `.sync/contact-snapshots/{source_id}.json`. Use serde_json since Contact already derives Serialize. Only serialize the CRM-relevant fields to a small struct (not the full Contact which includes etag, source, etc that change on every sync).
       - Define a small `#[derive(Serialize, Deserialize, PartialEq)] struct ContactSnapshot { name, email, phone, company, role, website, birthday }` with `From<&Contact>` impl.
       - Add `read_contact_snapshot(crm_root: &Path, source_id: &str) -> Option<ContactSnapshot>`
       - Add `contact_fields_changed(crm_root: &Path, source_id: &str, contact: &Contact) -> bool` that loads the cached snapshot, converts current Contact to ContactSnapshot, and compares with PartialEq. Returns true if no snapshot exists (conservative: assume changed).

    2. In src/sync/push.rs, replace the string comparison in compute_push_changeset (lines 130-145):
       - REMOVE the block that serializes via merge_contact_to_vcard and compares `serialized == *cached_text`
       - REPLACE with: `if !vcard_write::contact_fields_changed(crm_root, &source_id, &cf.contact) { continue; }` to skip unchanged contacts
       - When a contact IS changed, still read the cached vCard for the update tuple: `let cached = vcard_write::read_cached_vcard(crm_root, &source_id); updates.push((cf, cached.unwrap_or_default()));`

    3. In src/commands/sync.rs, cache Contact snapshot after pull:
       - After successful create_new_contact, call `vcard_write::cache_contact_snapshot(&crm_root, &uid, &mapped.contact)?`
       - After successful update_existing_contact, call `vcard_write::cache_contact_snapshot(&crm_root, &uid, &mapped.contact)?`
       - This ensures the snapshot matches what was pulled, so unchanged contacts won't trigger false updates

    4. In src/sync/push.rs execute_push, update snapshot after successful push:
       - After successful create (line 257 area), call `vcard_write::cache_contact_snapshot(crm_root, &new_uuid, &cf.contact)` (ignore errors with eprintln warning)
       - After successful update (line 331 area), call `vcard_write::cache_contact_snapshot(crm_root, &cf.contact.source_id, &cf.contact)`
       - After successful force-push conflict (line 431 area), same pattern

    5. Update existing tests in push.rs to work with new comparison:
       - test_icloud_contact_with_matching_cache_skipped: Instead of writing a merged vCard to cache, write a contact snapshot via cache_contact_snapshot
       - test_icloud_contact_with_different_cache_goes_to_updates: Write a snapshot with different name, then check contact goes to updates
       - test_mixed_contacts_categorized_correctly: Update the "unchanged" contact setup to use snapshot caching

  <name>Task 2: Fix vCard merge to preserve params and include NOTE</name>
  <files>src/sync/vcard_write.rs</files>
  <behavior>
    - Test: merge_contact_to_vcard preserves EMAIL TYPE params from cached vCard when email value is unchanged
    - Test: merge_contact_to_vcard preserves TEL TYPE params from cached vCard when phone value is unchanged
    - Test: merge_contact_to_vcard outputs NOTE property when contact has notes in cached vCard
    - Test: add_crm_entries uses consistent N encoding (same VCardValue type as contact_to_vcard)
    - Test: merge preserves property ordering (CRM props stay in original position, not moved to end)
  </behavior>
  <action>
    Fix three bugs in vcard_write.rs that cause data loss when pushing vCards:

    1. **Fix property reordering in merge_contact_to_vcard** (lines 114-135):
       - Instead of stripping ALL CRM_MAPPED_PROPERTIES and appending at end, do an IN-PLACE replacement strategy:
       - Parse the cached vCard. Iterate entries. For each entry:
         - If it's a CRM_MAPPED_PROPERTY: mark as "to be replaced" but remember its position and group
         - If it's NOT a CRM_MAPPED_PROPERTY: keep as-is
       - Build replacement entries from Contact data (similar to current add_crm_entries logic)
       - For properties that exist in BOTH cached and Contact (e.g., FN, N, ORG, TITLE, URL, BDAY): replace in-place at the original position
       - For EMAIL/TEL: these are multi-value. Match by value where possible to preserve params. For cached EMAIL entries whose value still exists in contact.email, keep the cached entry (preserving TYPE params). For new emails not in cache, append bare entries. Remove cached emails not in contact.email.
       - For NOTE: extract from cached vCard (since Contact model doesn't store notes) and preserve in-place. Do NOT strip it.
       - Approach: Build a new entries Vec by walking the cached entries in order. When hitting a CRM property, substitute the Contact's value. Track which Contact values have been placed. Append any remaining Contact values at the end.

    2. **Fix N encoding inconsistency** in add_crm_entries (line 150):
       - Change `VCardValue::Component(vec![...])` to use the same multi-value `VCardValue::Text` approach as contact_to_vcard (line 40-46), OR change contact_to_vcard to use Component. Pick ONE encoding and use it consistently in both places.
       - Recommendation: Use `.with_values(vec![VCardValue::Text(...), ...])` in both places since that was already validated as producing correct `N:Family;Given;;;` output per the existing test test_contact_to_vcard_has_n_structured.

    3. **Add NOTE preservation** in the merge function:
       - Remove VCardProperty::Note from CRM_MAPPED_PROPERTIES (since the Contact model doesn't have a notes field, stripping NOTE destroys data with no way to re-add it)
       - This single change means NOTE entries in cached vCards will be preserved through the retained entries filter, just like X-ABUID and PHOTO are preserved

    4. **Preserve EMAIL/TEL params during merge**:
       - When re-adding EMAIL entries in the in-place replacement, if the email value matches a cached EMAIL entry's value, copy the cached entry's params (TYPE=INTERNET,HOME etc.) onto the new entry using `.with_params(cached_entry.params.clone())`
       - Same for TEL entries: match by value, copy params
       - For new emails/phones not in cache: add bare (no params), which is the current behavior

    Update existing merge tests and add new ones for param preservation and NOTE.
