<task type="auto">
  <name>Task 2: Extract CRUD business logic into ops functions, thin-wrap CLI handlers</name>
  <files>src/ops/contact.rs, src/commands/add.rs, src/commands/list.rs, src/commands/search.rs, src/commands/show.rs, src/commands/edit.rs, src/commands/log.rs, src/commands/due.rs, src/commands/delete.rs, src/commands/archive.rs</files>
  <action>
Extract business logic from each command handler into ops/contact.rs functions. Each ops function takes `root: &Path` plus plain typed arguments, returns `Result<TypedResult, OpsError>`. Each command handler becomes: find_crm_root() + call ops + format output.

**For each command, follow this pattern:**

1. **add.rs**: Extract lines between `find_crm_root()` and `format::output()` into `ops::add(root: &Path, name: &str) -> Result<AddResult, OpsError>`. The ops function creates the Contact, generates frontmatter, writes via store, returns AddResult.

2. **list.rs**: Extract into `ops::list(root: &Path, tag: Option<&str>) -> Result<Vec<ContactSummary>, OpsError>`. Loads contacts, optionally filters by tag, maps to ContactSummary.

3. **search.rs**: Extract into `ops::search(root: &Path, query: &str) -> Result<Vec<SearchMatch>, OpsError>` (or whatever the match type is called). Loads contacts, filters by query, returns matches.

4. **show.rs**: Extract into `ops::show(root: &Path, name: &str) -> Result<ContactDetail, OpsError>`. Uses find_single_contact internally (ops owns fuzzy matching per user decision).

5. **edit.rs**: Extract into `ops::edit(root: &Path, name: &str, sets: &[String]) -> Result<EditResult, OpsError>`. Parses key=value pairs, applies updates via frontmatter functions, validates, writes.

6. **log.rs**: Extract into `ops::log_interaction(root: &Path, name: &str, interaction_type: &str, summary: &str, notes: Option<&str>) -> Result<LogResult, OpsError>`. Includes the interaction log append, last_contacted update, next_follow_up calculation. The `next_follow_up` function was already moved in Task 1.

7. **due.rs**: Extract into `ops::due(root: &Path) -> Result<Vec<DueContact>, OpsError>`. Loads contacts, filters to those with overdue or upcoming follow-ups.

8. **delete.rs**: Implement two-phase pattern per CONTEXT.md:
   - `ops::find_delete_target(root: &Path, name: &str) -> Result<DeleteTarget, OpsError>` -- finds contact, returns info
   - `ops::confirm_delete(root: &Path, name: &str) -> Result<DeleteResult, OpsError>` -- actually deletes the file
   - CLI handler: calls find_delete_target, prompts if not --yes, calls confirm_delete if confirmed

9. **archive.rs**: Extract into `ops::archive(root: &Path, name: &str) -> Result<ArchiveResult, OpsError>` and `ops::unarchive(root: &Path, name: &str) -> Result<ArchiveResult, OpsError>`.

**Error mapping pattern:** When calling store/frontmatter functions that return `anyhow::Result`, map errors:
```rust
store::some_function(args).map_err(|e| OpsError::Internal(e.to_string()))?;
```

For `find_single_contact` failures, parse the error message to produce `OpsError::NotFound` or `OpsError::AmbiguousMatch` as appropriate. Alternatively, refactor find_single_contact to return a more structured error that ops can match on.

**Anti-patterns to avoid:**
- Do NOT import `OutputFormat` or `format::` in ops/contact.rs
- Do NOT call `find_crm_root()` in any ops function
- Do NOT import anything from `crate::commands::*` in ops
- Do NOT add `colored` crate to ops imports
- Keep `Display` impls (with colored output) in command files, not ops

After all extractions, every command handler should be ~5-10 lines: find root, call ops, format output.
