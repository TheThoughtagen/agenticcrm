# Phase 12: Release Pipeline with Cross-Platform Builds, Homebrew, Chocolatey, and Install Script - Research

**Researched:** 2026-03-09
**Domain:** Rust release engineering, cross-platform binary distribution, package manager publishing
**Confidence:** HIGH

## Summary

AgenticCRM (`acrm`) is a Rust CLI tool with platform-specific dependencies (keyring with `apple-native` feature, reqwest with native TLS via `security-framework` on macOS). The release pipeline needs to produce binaries for macOS (ARM64 + x86_64), Linux (x86_64), and Windows (x86_64), then distribute them via GitHub Releases, Homebrew tap, a shell/PowerShell install script, and optionally Chocolatey.

**cargo-dist** (v0.31.0, Feb 2026) is the standard tool for this. It generates the entire GitHub Actions release workflow, builds cross-platform binaries, creates GitHub Releases with artifacts, and produces shell/PowerShell installers and Homebrew formulae out of the box. It replaces the need to hand-roll CI matrices, artifact packaging, and installer scripts. Chocolatey is NOT supported by cargo-dist; it would need a manual package if required.

**Primary recommendation:** Use cargo-dist for the full release pipeline. Add release-plz for automated version bumping and changelog generation. Defer Chocolatey to a future phase since cargo-dist does not support it and Windows users can use the PowerShell installer instead.

## Architecture Patterns

### Recommended Project Structure
```
.github/
├── workflows/
│   ├── release.yml          # Generated by cargo-dist (tag-triggered releases)
│   └── release-plz.yml     # release-plz PR automation
Cargo.toml                   # [dist] section added by cargo-dist init
CHANGELOG.md                 # Generated by release-plz/git-cliff
```

### Pattern 1: cargo-dist Init and Configuration
**What:** cargo-dist adds a `[dist]` (or `[workspace.metadata.dist]`) section to Cargo.toml and generates `.github/workflows/release.yml`
**When to use:** Initial setup and whenever targets/installers change
**Example:**
```toml
# In Cargo.toml
[dist]
cargo-dist-version = "0.31.0"
ci = ["github"]
installers = ["shell", "powershell", "homebrew"]
targets = [
    "aarch64-apple-darwin",
    "x86_64-apple-darwin",
    "x86_64-unknown-linux-gnu",
    "x86_64-pc-windows-msvc",
]
tap = "TheThoughtagen/homebrew-tap"
publish-jobs = ["homebrew"]
pr-run-mode = "plan"
install-updater = true
```

### Pattern 2: Tag-Triggered Release Flow
**What:** Pushing a version tag triggers the full release pipeline
**When to use:** Every release
**Flow:**
1. release-plz opens a PR with version bump + changelog
2. Merge the PR
3. release-plz creates a git tag (e.g., `v0.2.0`)
4. Tag push triggers cargo-dist workflow
5. cargo-dist builds binaries for all targets
6. cargo-dist creates GitHub Release with artifacts
7. cargo-dist publishes Homebrew formula to tap
8. cargo-dist generates shell/PowerShell install scripts

### Pattern 3: release-plz GitHub Action
**What:** Automated release PR maintenance
**When to use:** Runs on every push to main
**Example:**
```yaml
# .github/workflows/release-plz.yml
name: Release-plz
on:
  push:
    branches: [main]
permissions:
  pull-requests: write
  contents: write
jobs:
  release-plz:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: dtolnay/rust-toolchain@stable
      - uses: release-plz/action@v0.5
        env:
          GITHUB_TOKEN: ${{ secrets.RELEASE_PLZ_TOKEN }}
          CARGO_REGISTRY_TOKEN: ${{ secrets.CARGO_REGISTRY_TOKEN }}
```

### Anti-Patterns to Avoid
- **Hand-rolling release CI:** cargo-dist generates and maintains the workflow; editing it manually causes drift when re-running `dist init`
- **Using GITHUB_TOKEN for release-plz:** Must use a Personal Access Token (RELEASE_PLZ_TOKEN) so that tag creation triggers downstream workflows
- **Cross-compiling macOS from Linux:** Security.framework and keyring apple-native require macOS SDK; cargo-dist uses native macOS runners instead
- **Forgetting `fetch-depth: 0`:** release-plz needs full git history for changelog generation and version determination

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-platform binary builds | Custom GitHub Actions matrix with cross-rs | cargo-dist | Handles runner selection, build flags, artifact packaging, checksums |
| Shell install script | Custom `install.sh` | cargo-dist shell installer | Handles platform detection, PATH setup, verification, updates |
| PowerShell install script | Custom `install.ps1` | cargo-dist PowerShell installer | Same as above for Windows |
| Homebrew formula | Manual Ruby formula | cargo-dist Homebrew publisher | Auto-generates formula, updates tap on release |
| Changelog | Manual CHANGELOG.md edits | git-cliff via release-plz | Parses conventional commits, consistent format |
| Version bumping | Manual Cargo.toml edits | release-plz | Semver-aware, detects API breaking changes |

**Key insight:** cargo-dist is specifically designed so you never maintain release infrastructure manually. Running `dist init` regenerates everything. The moment you hand-edit the generated workflow, you take on maintenance burden that cargo-dist would handle for you.

## Common Pitfalls

### Pitfall 1: Platform-Specific Dependencies Block Cross-Compilation
**What goes wrong:** The `keyring` crate with `apple-native` feature requires macOS Security.framework. Linux builds from Docker containers cannot link against it.
**Why it happens:** cargo-dist by default uses native runners (macOS for macOS targets, Linux for Linux targets), so this is NOT an issue with cargo-dist. It would only matter if attempting cross-compilation from a single platform.
**How to avoid:** Use cargo-dist's default strategy of native runners per platform. Do not attempt to cross-compile macOS targets from Linux.
**Warning signs:** Link errors mentioning `Security.framework` or `SecKeychainItem` during Linux builds.

### Pitfall 2: keyring Feature Flags Per Platform
**What goes wrong:** The `keyring` crate uses `apple-native` feature, but Linux needs `linux-native` or `sync-secret-service`, and Windows needs `windows-native`. With only `apple-native` enabled, Linux/Windows builds get a mock credential store.
**Why it happens:** Cargo.toml currently specifies `keyring = { features = ["apple-native"] }` which is macOS-only.
**How to avoid:** Use conditional platform dependencies in Cargo.toml:
```toml
[target.'cfg(target_os = "macos")'.dependencies]
keyring = { version = "3.6.3", features = ["apple-native"] }

[target.'cfg(target_os = "linux")'.dependencies]
keyring = { version = "3.6.3", features = ["linux-native"] }

[target.'cfg(target_os = "windows")'.dependencies]
keyring = { version = "3.6.3", features = ["windows-native"] }
```
**Warning signs:** Sync features silently failing on non-macOS platforms.

### Pitfall 3: GITHUB_TOKEN Cannot Trigger Downstream Workflows
**What goes wrong:** release-plz creates a tag using GITHUB_TOKEN, but cargo-dist workflow (triggered by tag push) never fires.
**Why it happens:** GitHub Actions does not trigger workflows from events created by GITHUB_TOKEN to prevent infinite loops.
**How to avoid:** Create a Personal Access Token with `repo` scope, add as `RELEASE_PLZ_TOKEN` secret, use it in release-plz action.
**Warning signs:** Tags appear in repo but no release workflow runs.

### Pitfall 4: Homebrew Tap Repository Must Exist Before First Release
**What goes wrong:** cargo-dist release fails at the Homebrew publish step.
**Why it happens:** cargo-dist pushes the formula to the tap repo; if it doesn't exist, the push fails.
**How to avoid:** Create the `TheThoughtagen/homebrew-tap` repository before the first release. Add a `HOMEBREW_TAP_TOKEN` secret with `repo` scope.
**Warning signs:** Release workflow partially succeeds (binaries uploaded) but Homebrew step fails.

### Pitfall 5: Forgetting to Update cargo-dist CI After Config Changes
**What goes wrong:** Adding new targets or installers to `[dist]` but the GitHub Actions workflow still uses the old configuration.
**Why it happens:** `dist init` must be re-run to regenerate the workflow file.
**How to avoid:** Always run `dist init` after changing `[dist]` config, then commit the updated workflow.
**Warning signs:** `dist plan` shows different targets than what CI actually builds.

### Pitfall 6: Chocolatey Is Not Supported by cargo-dist
**What goes wrong:** Attempting to add Chocolatey as an installer in cargo-dist config.
**Why it happens:** cargo-dist supports shell, powershell, npm, homebrew, and msi -- NOT Chocolatey.
**How to avoid:** Use the PowerShell installer for Windows users. If Chocolatey is essential, create a manual `.nuspec` package as a separate workflow step.
**Warning signs:** `dist init` does not offer Chocolatey as an option.

```bash

cargo dist init --yes

# Preview what CI will build
cargo dist plan
```

### Homebrew Tap Setup
```bash
# Create the tap repository on GitHub
gh repo create TheThoughtagen/homebrew-tap --public --description "Homebrew formulae for AgenticCRM"

# Add secrets to the source repository
gh secret set HOMEBREW_TAP_TOKEN --body "ghp_your_token_here"
gh secret set RELEASE_PLZ_TOKEN --body "ghp_your_token_here"
# CARGO_REGISTRY_TOKEN only if publishing to crates.io
gh secret set CARGO_REGISTRY_TOKEN --body "your_crates_io_token"
```

### End-User Installation Commands
```bash
# macOS / Linux (shell installer)
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/TheThoughtagen/agenticcrm/releases/latest/download/acrm-installer.sh | sh

# Windows (PowerShell installer)
powershell -ExecutionPolicy ByPass -c "irm https://github.com/TheThoughtagen/agenticcrm/releases/latest/download/acrm-installer.ps1 | iex"

# Homebrew
brew install TheThoughtagen/tap/acrm

# From source (existing)
cargo install --git https://github.com/TheThoughtagen/agenticcrm.git
```

## Open Questions

1. **Chocolatey: Build or Defer?**
   - What we know: cargo-dist does not support Chocolatey. A manual `.nuspec` + build script would be needed.
   - What's unclear: Whether Windows users would strongly prefer `choco install acrm` over the PowerShell installer
   - Recommendation: Defer Chocolatey. PowerShell installer covers Windows. Add Chocolatey as a future enhancement if demand arises.

2. **crates.io Publishing**
   - What we know: Cargo.toml metadata is complete (name, description, license, repository, keywords, categories). release-plz can automate `cargo publish`.
   - What's unclear: Whether the project is ready for crates.io (version 0.1.0, may want to stabilize first)
   - Recommendation: Include crates.io publishing in the pipeline but mark it as optional (can be enabled when ready)

3. **Linux keyring Backend**
   - What we know: `linux-native` requires `libsecret-1-dev` or similar at build time. The README already notes Linux needs `libsecret` or `gnome-keyring`.
   - What's unclear: Whether CI runners have `libsecret-1-dev` installed by default
   - Recommendation: Add `apt-get install libsecret-1-dev` to the Linux build step, or use `sync-secret-service` feature which may have fewer build deps. Test during implementation.

4. **ARM64 Linux Target**
   - What we know: cargo-dist supports `aarch64-unknown-linux-gnu` but it requires cross-compilation (GitHub has no native ARM64 Linux runners yet)
   - What's unclear: Whether the keyring + reqwest dependencies cross-compile cleanly for ARM64 Linux
   - Recommendation: Start with x86_64 Linux only. Add ARM64 Linux later if demand warrants it.
