  <name>Task 1: Add MCP dependencies and create CrmServer with ServerHandler</name>
  <files>Cargo.toml, src/mcp/mod.rs, src/mcp/server.rs</files>
  <action>
1. Add dependencies to Cargo.toml:
   ```toml
   rmcp = { version = "1.1", features = ["server", "macros", "transport-io", "transport-streamable-http-server"] }
   tokio = { version = "1", features = ["full"] }
   axum = "0.8"
   schemars = "0.8"
   tracing = "0.1"
   tracing-subscriber = { version = "0.3", features = ["env-filter"] }
   ```

2. Create `src/mcp/mod.rs`:
   - Declare submodules: `pub mod server;` and `pub mod tools;`
   - Define `CrmServer` struct with fields:
     - `root: PathBuf` (contacts directory root)
     - `write_lock: Arc<tokio::sync::Mutex<()>>` (for MCP-12 concurrent write safety)
     - `allow_sync: bool` (for MCP-10 sync permission gate)
     - `tool_router: tools::CrmToolRouter` (tool dispatch — the exact type depends on rmcp macro output; may need to be the generated ToolRouter type)
   - Implement `Clone` for CrmServer (required by rmcp for HTTP transport — Arc fields make this cheap)
   - Create `pub async fn serve_stdio(server: CrmServer) -> anyhow::Result<()>` that:
     - Initializes tracing with stderr writer (`tracing_subscriber::fmt().with_writer(std::io::stderr).with_ansi(false).init()`) — CRITICAL: stdout is the MCP JSON-RPC channel
     - Calls `server.serve(rmcp::transport::stdio()).await?` to start the MCP server
     - Calls `service.waiting().await?` to block until client disconnects
   - Include a helper function `ops_err_to_mcp(e: OpsError) -> McpError` that maps:
     - `NotFound` -> `McpError::resource_not_found(...)` (or `internal_error` if that variant doesn't exist in rmcp 1.1)
     - `AmbiguousMatch` -> `McpError::invalid_params(...)`
     - `ValidationFailed` -> `McpError::invalid_params(...)`
     - All others -> `McpError::internal_error(...)`
     - NOTE: Check rmcp 1.1 docs for exact McpError constructor signatures. If `resource_not_found` or `invalid_params` don't exist, fall back to `internal_error` with descriptive messages for all variants.

3. Create `src/mcp/server.rs`:
   - Implement `#[tool_handler]` on `impl ServerHandler for CrmServer`
   - Implement `get_info()` returning ServerInfo with:
     - `protocol_version: ProtocolVersion::V_2025_03_26`
     - capabilities: `enable_tools()` and `enable_resources()`
     - server_info name: "acrm", version: `env!("CARGO_PKG_VERSION")`
     - instructions: "AgenticCRM - a personal CRM. Search, view, add, edit, log interactions, delete, archive contacts, and manage follow-ups."

NOTE on rmcp API: The rmcp 1.1 SDK is only days old. If macro syntax differs from research examples, consult `cargo doc --open` output or compiler errors. The core pattern is: `#[tool_router]` on impl block with `#[tool]` methods, and `#[tool_handler]` on ServerHandler impl to wire them together. Adapt to actual API as needed.

<task type="auto">
  <name>Task 2: Implement read-only MCP tools and wire Serve CLI command</name>
  <files>src/mcp/tools.rs, src/main.rs</files>
  <action>
1. Create `src/mcp/tools.rs` with `#[tool_router]` impl on CrmServer (or a dedicated tools struct — follow rmcp's pattern for separating tool methods):
   - Define parameter structs with `serde::Deserialize` + `schemars::JsonSchema`:
     - `SearchParams { query: String }` with schemars description "Search query matching name, company, tags, email, or notes"
     - `ShowParams { name: String }` with description "Contact name or partial name match"
     - (DueParams: no parameters — use empty struct or unit)

   - Implement `#[tool]` methods, each wrapping ops calls in `spawn_blocking`:

   a) `search_contacts(&self, params: SearchParams) -> CallToolResult`:
      - Clone `self.root`, spawn_blocking `ops::contact::search(&root, &params.query)`
      - Serialize results to JSON, return `CallToolResult::success(vec![Content::text(json)])`
      - Map errors through `ops_err_to_mcp`

   b) `show_contact(&self, params: ShowParams) -> CallToolResult`:
      - Clone `self.root`, spawn_blocking `ops::contact::show(&root, &params.name)`
      - Serialize the ContactDetail to JSON (includes raw_frontmatter and body)
      - Return as Content::text

   c) `due_followups(&self) -> CallToolResult`:
      - Clone `self.root`, spawn_blocking `ops::contact::due(&root)`
      - Serialize Vec<DueContact> to JSON
      - Return as Content::text
      - If empty list, return success with message "No contacts due for follow-up"

2. Update `src/main.rs`:
   - Add `mod mcp;` declaration
   - Add Serve variant to Commands enum:
     ```rust
     /// Start MCP server for AI agent integration
     Serve {
         /// Use HTTP transport instead of stdio
         #[arg(long)]
         http: bool,
         /// HTTP port (default: 3000)
         #[arg(long, default_value = "3000")]
         port: u16,
         /// Allow sync operations (disabled by default for safety)
         #[arg(long)]
         allow_sync: bool,
     }
     ```
   - Add match arm for Commands::Serve that:
     - Determines `root` path (same logic as existing commands use for contacts dir)
     - Creates `CrmServer::new(root, allow_sync)`
     - Creates tokio runtime: `tokio::runtime::Runtime::new()?`
     - For now, only handle stdio: `rt.block_on(mcp::serve_stdio(server))?`
     - HTTP transport will be added in plan 02

IMPORTANT: All ops calls MUST be wrapped in `tokio::task::spawn_blocking()` because the ops layer uses synchronous file I/O and reqwest::blocking (which panics inside tokio runtime).
